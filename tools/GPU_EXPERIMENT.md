# GPU 搜索原型验证（2026-09-20）

原型已经在 NVIDIA GeForce RTX 4080 16GB 上运行真实 CUDA 搜索。
Web 服务已通过默认关闭的“GPU 加速（实验）”勾选框调用它；游戏一键整理仍不调用。
未安装 CuPy、CUDA 不可用或构筑超出当前支持范围时，Web 求解会自动回退原 CPU 路径。

## 实现与范围

- `tools/gpu_search.cu`：4096 个独立搜索起点，每个默认尝试 512 次物品交换或石板转向；位置排列保证不重叠。
- `tools/gpu_search.py`：构建效果表、上传数据、启动 GPU、取回最佳布局，并用现有 CPU 规则重新验证分数。
- `app/solver.py`：接受可选 `initial_placements`，转换为第一阶段位置提示。等价实例按现有对称性约束排序，跳过共享常量，并识别候选去重后的等价旋转。
- GPU 比较整数三元组：加权生效等级、生效等级总和、起效神器数量。CP-SAT 继续处理完整目标与最优性证明。
- 当前支持无位置启用条件的普通神器、基础等级、等级上限、静态石板加减等级、倍率、禁用格和原生双倍格。
- 固定位置/旋转、最低/固定等级、特殊效果优先、神器位置启用条件、动态石板条件会明确拒绝，尚不支持。解锁效果在当前无位置条件的支持范围中不改变起效判定。
- 这是多起点爬山搜索，可能停在局部最优；提示也不保证被 CP-SAT 采用。因此原型会比较两边的完整目标顺序，在 CP-SAT 返回较差结果时保留经 CPU 校验的 GPU 解。

## 复现

项目原有 Python 环境中安装可选依赖（本次安装的是 CuPy 14.2.0，使用已有 CUDA Toolkit 12.1）：

```powershell
.\runtime\Scripts\python.exe -m pip install -r requirements-gpu.txt
.\runtime\Scripts\python.exe -m tools.benchmark_gpu --repeats 3 --steps 2048
.\runtime\Scripts\python.exe -m tools.benchmark_gpu --repeats 1 --steps 2048 --full-time --output artifacts/gpu-benchmark-realistic-full.json
.\runtime\Scripts\python.exe -m pytest tests -q -p no:cacheprovider
```

需要 NVIDIA 显卡和 CUDA 12 Toolkit。可选安装方式见 [CuPy 官方安装说明](https://docs.cupy.dev/en/stable/install.html)。
普通 CPU 运行不需要该依赖。

## 方法

三组来自真实目录、程序化选择的高占用构筑：30 格（23 神器、5 石板）、
42 格（33 神器、7 石板）、60 格（48 神器、10 石板）。每组独立抽取神器、
石板和 0～2 级局内基础等级，使用默认权重 5。具体随机种子保存在基准脚本中。
这些是目录生成的可复现样本，仍不是玩家实际局面的捕获数据。
每组采用 15 秒上限与快速模式，各重复 3 次，CPU 使用 8 个工作线程。
交替执行纯 CPU 与混合方案；GPU 搜索种子为 1～3，CP-SAT 保持原有种子 1。

总耗时包含 GPU 效果表准备、内存传输、GPU 搜索、取回、CPU 种子校验、
CP-SAT 建模/搜索、布局修复及最终校验；两侧均不计模块导入与目录加载。
不会先花 CPU 时间求参考解，也不使用磁盘结果缓存。
GPU 初始化在热进程对照前完成，未计入表中请求耗时；本机进程初始化约 0.4 秒。
CP-SAT 使用软时限，实际耗时会略超出预算；原始数据保留这些超时，不裁剪。

## 实测

下表均为 3 次中位数；分数为主目标，不是加速倍数。没有一组证明最优，
这符合“时限内返回优质解”的测试目标。

| 构筑 | 预算 | CPU 分数 | 混合分数 | CPU 实际总耗时 | 混合实际总耗时 | GPU 准备至种子校验 |
|---|---:|---:|---:|---:|---:|---:|
| 30 格 | 15s | 145 | 145 | 5056.08ms | 4764.65ms | 80.86ms |
| 42 格 | 15s | 240 | 270 | 8044.56ms | 5859.74ms | 150.37ms |
| 60 格 | 15s | 315 | 380 | 12086.33ms | 8993.04ms | 303.39ms |

基础 30 格的最终质量相同。42 格主目标中位数提高 12.5%，60 格提高约 20.6%；
混合方案也更早触发“连续 2 秒无改进”停止条件。所有 18 次最终结果都通过 CPU 校验。
60 格混合组有两次 CP-SAT 没有保住提示解，GPU 保底逻辑正确返回了更高分的 GPU 布局。

另以同样三组构筑各运行一次关闭快速停止、用满 15 秒的对照；两边分数分别为
30 格 145/145、42 格 270/270、60 格 380/380。说明本轮收益主要是更早到达优质解，
在完整 15 秒内纯 CPU 可以追平这些单一样本。这项单次结果不支持“GPU 必然提高 15 秒终局质量”。

原始数据：`artifacts/gpu-benchmark-realistic-final.json`（18 次）、
`artifacts/gpu-benchmark-realistic-full.json`（6 次用满时限对照）。
这些文件位于项目已忽略的 artifacts 目录，可通过脚本重新生成。

## 结论与下一步

在本机、这些普通构筑上，GPU 生成种子加 CP-SAT 搜索能明显缩短 42～60 格构筑
到达高质量解的时间；基础 30 格没有质量收益。用满 15 秒的单次样本中纯 CPU 均能追平，
所以现有证据支持“更快得到好解”，尚未支持“同样 15 秒一定得到更高分”。
它没有证明对所有构筑有效，也没有评估最优性证明速度。
当前对照也没有区分 GPU 硬件和新增启发式算法各自的贡献；若要评估是否必须依赖显卡，
还需加入同类 CPU 启发式对照。

Web 接入已具备取消、总时限核算和不可用时的 CPU 回退；实际背包中的完整规则仍未补齐，
超出上述支持范围的构筑会直接使用 CPU。
种子保底已经在原型中验证；下一项关键证据应来自游戏读取的匿名实际构筑集，
而不是继续增加合成样本。GPU 常驻初始化适合该项目的后台服务运行方式。
